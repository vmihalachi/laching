# AGENTS.md — Laching

Guide for coding agents (Claude Code reads it through `CLAUDE.md`). Humans start at `README.md`.

**What it is:** an MIT Swift package plus .NET packages and a Kotlin build with the generic parts of a menu bar, tray or
phone app: pure scheduling (`LachingCore` / `Laching.Core`), permission-free system signals, app-shell plumbing, a
purchase store (StoreKit, the Microsoft Store, Google Play), and the layer a desk companion app is built on
(`LachingCompanion` / `Laching.Companion`, its UI and `tools/`). Used by mybackhurts, sunnysays and Mister Pagliacci.
Beside them, `web/`: the `Laching.Web.*` NuGet packages for small ASP.NET Core sites behind Cloudflare (formerly
Webling), used by Adjudeca and sharing nothing else. The Swift code is the reference; the C# port replays its
conformance vectors, and the Kotlin port (`kotlin/`, for the Android apps) the scheduler's.

## Where things live

`Sources/Laching{Core,System,Shell,Companion,CompanionUI,Store,Testing}/` are the Swift products, one folder each,
with `Tests/<Product>Tests/`; `dotnet/` holds their C# mirrors (`Laching.Core`, `Laching.Companion`,
`Laching.Companion.Shell`, `Laching.Testing`, `Laching.Windows`, `Laching.Windows.Companion`, their tests and
`Fixture.App`); `kotlin/` the Kotlin build the Android apps include (`:core`, `:android`, `:testing`);
`conformance/` the generated vectors (never hand-edit); `tools/` the companion apps' tools;
`scripts/` the repo's own scripts; `plans/` the released designs' record; `web/` the web packages (`src/`, `tests/`,
their own solution and build files); `site/` the project site (static HTML, published by `pages.yml`). The
folder-by-folder map, with what each
product imports and what runs where, is `docs/layout.md`.

## Commands

```sh
swift build && swift test                      # needs macOS (LachingSystem/Shell/Store import AppKit, CoreAudio, StoreKit)
LACHING_WRITE_CONFORMANCE=1 swift test --filter 'ConformanceTests/testWriteVectors'   # or scripts/conformance.sh
xcrun swift-format lint -r --strict --configuration .swift-format Sources Tests
cd dotnet && dotnet test Laching.Core.Tests   # anywhere with the .NET 10 SDK (Laching.Windows builds on Windows only)
cd dotnet && dotnet test Laching.Companion.Tests   # the companion vectors, the same anywhere
cd dotnet && dotnet test Laching.Companion.Shell.Tests   # the companion shell's logic, the same anywhere
cd dotnet && dotnet test Laching.Testing.Tests   # the mocks, the conformance helpers and the fixtures, the same anywhere
cd dotnet && dotnet test Laching.Tests.slnf   # the four above in one run (what verify.sh runs)
cd dotnet && dotnet test Laching.Windows.Companion.Tests   # Windows only: the speaker, the chime and the Windows shell's services
dotnet run --project dotnet/Fixture.App        # Windows only: the fixture app, for the checks by hand
scripts/fixture-screenshots.ps1 [-Only home]   # Windows only: the fixture's windows to PNGs, light and dark; fails on layout problems (-Only runs hidden; -NoBuild to repeat)
python3 tools/windows/check-winui.py dotnet/Fixture.App dotnet/Laching.Windows.Companion   # the WinUI traps under Native AOT
dotnet format whitespace dotnet --folder       # C# style (dotnet/.editorconfig)
cd kotlin && ./gradlew :core:test :testing:test   # a JDK 17, anywhere; replays the scheduler vectors
cd kotlin && ./gradlew :android:assembleDebug     # needs the Android SDK
cd kotlin && ktlint "**/*.kt" "**/*.kts" "!**/build/**"   # Kotlin style (kotlin/.editorconfig; kotlin.yml pins ktlint)
python3 tools/tests/run.py [l10n] [--jobs N]  # the tools' tests, side by side (one process per CPU; a word filters by file name)
dotnet test web/Laching.Web.sln                # the web packages; Jobs tests need PostgreSQL (LACHING_WEB_TEST_POSTGRES, or localhost:5432)
web/scripts/tailwind-sample.sh                 # packs Laching.Web.Tailwind and builds the sample with it
scripts/verify.sh                              # runs what applies to your changes; --all for everything
# a Stop hook runs scripts/verify.sh --fast on the files you edited; fix what it reports before ending
```

In a Linux container only the .NET side and the Kotlin side's `:core` and `:testing` run (a JDK 17; the `:android` build
needs the SDK, so `kotlin.yml` builds it). Verify Swift through `swift.yml` (push a branch, dispatch the workflow,
read the failed job's log). Vectors need the Swift code to regenerate: without a Mac, dispatch `regenerate-vectors.yml`
on your branch and pull the commit it pushes. It refuses the default branch (its first step fails there), so a vector
change reaches `master` only through a pull request.

## Planned work

Planned work lives in [GitHub Issues](https://github.com/vmihalachi/laching/issues), not in files (`gh issue list`,
`gh issue view N`). Read the issue before starting and work only on what it says; a `decision` issue waits for the
owner's choice. Comment what you found as you go, tick the checkboxes, close it from the commit (`Fixes #N`).
Something found along the way is a new issue, not a note in a file. The labels and the shape of an issue:
`docs/issues.md`.

## Finding code

The map in `docs/layout.md`: every Swift file has a C# twin, at the same relative path unless the map says otherwise
(`LachingCore`'s `Drawing/` has none: it is Swift and Kotlin only), so `grep -rn` on a type name finds both sides. The
Kotlin twins are under `kotlin/*/src/main/kotlin/laching/` (the `port-to-kotlin` skill).

## Skills

Step-by-step procedures for the multi-step changes live in `.agents/skills/` (linked per skill from `.claude/skills/`, as a folder from `.junie/skills/` and `.github/skills/`). Read the matching `SKILL.md` before starting:

- `add-scheduler-behavior`: new or changed `ReminderScheduler` behavior, from config field to the C# and Kotlin ports.
- `port-to-csharp`: mirroring any Swift change in `dotnet/`.
- `port-to-kotlin`: mirroring a Swift change in `kotlin/`, or changing an Android service there.
- `change-tool`: adding or changing a tool in `tools/` or a `companion.json` key it reads.
- `release`: cutting a release (`release.yml`, a dry run first), what ships, moving the apps.

## Conventions

The short form; the full rules with their examples are in `docs/conventions.md`.

- **Public API is deliberate:** every public type gets a doc comment (what it does, needs and never does); keep the
  type names mybackhurts already uses.
- **Swift 6, strict concurrency, macOS 14+ and iOS 17+, no dependencies.** `LachingCore` is Foundation-only (plus
  CoreGraphics in `Drawing/`, on Apple platforms only) and `LachingCompanion` Foundation and Observation only (both
  build on Linux); AppKit, SwiftUI, CoreAudio, AVFoundation, IOKit and Carbon stay in `LachingSystem`, `LachingShell` or
  `LachingCompanionUI`.
- **Package code never names an app** and ships no strings: apps inject their bank, defaults, skins, palette,
  voices and every label (`Text`, string or copy struct); `tools/` reads everything app-specific from `companion.json`.
- **No permission prompts, no network.**
- **No migrations for renamed persisted keys:** when a rename changes a settings, cache or preference key
  (`deskling.*` → `laching.*`), the old value is dropped; mention it in one line at most, with no shim, pull request or
  release note unless the owner asks.
- **Behavior changes are additive and vector-tested:** a config field whose default keeps every vector byte-identical, a
  unit test, a vector case and the C# port (and the Kotlin one, for the scheduler) in the same change.
  `conformance/companion` pins mechanism over fixtures; each app pins its own content.
- **Rasters never shear:** rotation, translation and uniform scale only; pose vectors pin affines, never pixels.
- **C# mirrors Swift** folder for folder and file for file, except `Drawing/` (Swift and Kotlin only); the deviations
  (the store under `Laching.Core/Store/`, `Laching.Testing`'s own layout, the companion shell mirrored by role) are
  marked in `docs/layout.md`. Source-generated JSON only: the apps publish with Native AOT.
- **Versioning:** SemVer, one tag per release, no changelog file: the release notes are the merged pull requests'
  titles, so label a breaking one `breaking`. A change never bumps or tags. The full rule is in `docs/conventions.md`,
  releasing in the `release` skill.
- Formatting is enforced in CI: `.swift-format` (4 spaces, 140 columns), `dotnet/.editorconfig`, `web/.editorconfig`
  and `kotlin/.editorconfig` (ktlint).
